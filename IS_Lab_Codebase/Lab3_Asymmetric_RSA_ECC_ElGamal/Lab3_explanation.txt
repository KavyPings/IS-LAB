--------------------------------------------------------------------------------
THE ONE IDEA THAT RUNS THROUGH THE WHOLE LAB : HYBRID ENCRYPTION
--------------------------------------------------------------------------------
No asymmetric algorithm can encrypt a large message.
  RSA-2048 with OAEP : maximum ~214 bytes
  ECC                : cannot encrypt at all, it only agrees on keys
  ElGamal mod p      : message must be a number smaller than p

So the standard answer to "encrypt a file/message with RSA/ECC/ElGamal" is:
  1. generate a RANDOM AES key
  2. AES-encrypt the data (fast, any size)
  3. protect the AES key with the asymmetric algorithm
     RSA     -> encrypt the key
     ECC     -> derive the key by ECDH with an ephemeral key pair (ECIES)
     ElGamal -> wrap the key as an ElGamal ciphertext
Write this in every answer; it is where the marks are.

--------------------------------------------------------------------------------
ALGORITHM SUMMARY
--------------------------------------------------------------------------------
RSA         n = p*q, phi = (p-1)(q-1), d = e^-1 mod phi
            encrypt c = m^e mod n    decrypt m = c^d mod n
            security: factoring n is hard

ElGamal     private x, public h = g^x mod p
            encrypt: random k, c1 = g^k, c2 = m * h^k   (both mod p)
            decrypt: s = c1^x, m = c2 * s^-1 mod p
            security: discrete logarithm
            randomised -> same message encrypts differently each time
            k MUST be fresh; reusing it leaks the plaintext

ECC         private d, public Q = d*G on the curve
            ECDH  : shared point = my_d * their_Q  (both sides get the same)
            ECIES : hash the shared point's x coordinate -> AES key
            ECDSA : signatures
            security: elliptic curve discrete logarithm
            P-256 = secp256r1 = prime256v1 (three names, one curve)

Diffie-Hellman  A = g^a, B = g^b, shared = g^(ab) mod p
            gives a key, NOT encryption and NOT authentication
            vulnerable to man-in-the-middle unless the public values are signed
            use the RFC 3526 group-14 prime instead of generating your own

--------------------------------------------------------------------------------
COMMON MISTAKES
--------------------------------------------------------------------------------
  * trying to RSA-encrypt a long message directly -> ValueError
  * forgetting that ECC needs ECIES/ECDH to "encrypt"
  * generating a 2048-bit safe prime for ElGamal in an exam (takes minutes) -
    use 256 bits for the demo and say so, or use a standard group
  * reusing k in ElGamal
  * using the raw DH shared number as an AES key - always hash it first
